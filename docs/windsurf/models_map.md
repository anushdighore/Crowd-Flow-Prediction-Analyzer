# Models Map

This document maps the main crowd-counting models to their **checkpoints**, **APIs**, **input modes**, and **outputs**. It is meant as a quick reference when reasoning about routing, payloads, and which artifacts (density map, heatmap, boxes, tracks, advanced metrics) are available where.

Models covered:

- CSRNet
- TMTB / VMamba
- YOLOv8 (including UnifiedCounter + tracking)
- MCNN (roadmap / partial support)

Issue IDs (W‑xxx) refer to `issues_overview.md`.

---

## CSRNet

### Role

- Canonical **density regression** baseline.
- Produces a **density map** and aggregated **count**.

### Checkpoints & config

- In `backend/config/config.yaml`:
  - `models.csrnet.checkpoint: "saved_models/checkpoints/pretrained/csrnet.pth"`.
- In `ml/src/models/csrnet/api.py` (not reproduced here):
  - Default checkpoint and device resolution logic.

### API surface

- **REST (image)**

  - `POST /api/v1/csrnet/count` → upload image, returns count & timings.
  - `POST /api/v1/csrnet/predict` → alias for `/count`.

- **REST (webcam-style single frame)**

  - `POST /api/v1/csrnet/webcam` → upload single frame, optimized for realtime sizing.

- **WebSocket (streaming)**
  - Live Webcam: `ws://localhost:8000/ws/count`
    - Used as **default model** when `model` is missing or unrecognized.
  - External Camera: `ws://localhost:8000/ws/external-camera`
    - Via `GatedModelRouter` when `model_type` is `"csrnet"`.

### Outputs

- Core fields:

  - `count` (float) and `rounded_count`/integer count.
  - `inference_time_ms`, `device`, `original_size`, `processed_size`.

- Density-related fields (when enabled):
  - `density_map` (internal representation; usually not sent directly).
  - `density_map_stats` (min, max, mean, sum) – especially in streaming `/ws/count`.
  - `heatmap` (data URL) – generated by `csrnet_api.generate_heatmap(density_map, image)`.

### Input modes

- **Upload Image**: primary model (alongside TMTB/YOLO).
- **Live Webcam**: currently used for **all** models when W‑001 is in effect.
- **External Camera**: one of the models under the gated router.
- **Video Upload**: basic support via CSRNet branch in `/ws/video-process`.

### Notes

- CSRNet is the most widely integrated model in the codebase and serves as the **fallback** whenever model routing fails (see W‑001).

## TMTB / VMamba

### Role

- High-accuracy **density regression** model (`TMTB` / `VMamba`).
- Intended as the “best accuracy” counterpart to CSRNet for dense scenes.

### Checkpoints & config

- In `backend/config/config.yaml`:

  - `models.available` includes `vmamba_tmtb`.
  - `models.vmamba_tmtb.checkpoint: "saved_models/checkpoints/pretrained/jhu_5.pth"`.

- In `ml/src/models/tmtb/api.py`:
  - Implements `predict(image, source=...)` and **optionally** density/heatmap functionality.

### API surface

- **REST (image)**

  - `POST /api/v1/tmtb/count`
  - `POST /api/v1/tmtb/predict` → alias for `/count`.

- **REST (webcam-style single frame)**

  - `POST /api/v1/tmtb/webcam`.

- **WebSocket (streaming)**
  - Live Webcam: intended via `/ws/count` with `model` resolving to TMTB.
    - Current backend condition: `model_type.lower() == "tmtb"`.
    - Frontend sends `"vmamba"` instead (see W‑001), so this branch is not reached today.
  - External Camera: via `GatedModelRouter` when `model_type` is `"tmtb"` or equivalent.

### Outputs

- Same core fields as CSRNet:
  - `count`, `raw_count`, `inference_time_ms`, `device`, `original_size`, `processed_size`.
- Density/heatmap:
  - Density maps and heatmaps can be generated in streaming contexts via the gated router or density APIs.

### Input modes

- **Upload Image**: supported via REST.
- **Live Webcam**: intended but currently blocked by naming mismatch.
- **External Camera**: available via gated router.
- **Video Upload**: not currently wired as a first-class branch.

### Notes

- The **naming triangle** is important:
  - UI: “VMamba TMTB”.
  - Multi-model server: `"vmamba"` → `"vmamba_tmtb"`.
  - Current `/ws/count`: expects `"tmtb"`.
- Fix W‑001 to make TMTB reachable from the webcam UI.

## YOLOv8 (with UnifiedCounter)

### Role

- **Object detection**-based crowd counting, with bounding boxes.
- Supports optional **Kalman-based tracking** and advanced crowd metrics via `UnifiedCounter`.

### Checkpoints & config

- YOLO variant mapping (in both `websocket_count` and other handlers):

  ```python
  yolo_model_map = {
    "yolo": "yolov8n.pt",
    "yolo-nano": "yolov8n.pt",
    "yolo-small": "yolov8s.pt",
    "yolo-medium": "yolov8m.pt",
    "yolo-large": "yolov8l.pt",
    "yolo-xlarge": "yolov8x.pt",
  }
  ```

- `ml/src/models/yolo/api.py`:

  - Handles `predict(image, checkpoint_path, return_boxes, visualize)`.
  - Exposes `generate_heatmap(boxes, original_image)` for YOLO-derived heatmaps.

- `ml/src/models/unified_counter.py`:
  - Wraps YOLOv8 with tracking and advanced analysis (`UnifiedCounter`).

### API surface

- **REST (image)**

  - `POST /api/v1/yolo/count` – boxes + aggregate count.
  - `POST /api/v1/yolo/detect` – adds `annotated_image` and richer detection stats.
  - `POST /api/v1/yolo/webcam` – webcam-optimized single-frame inference.
  - `POST /api/v1/yolo/track` – YOLO + Kalman tracker for trajectories.

- **Tracking utilities**

  - `POST /api/v1/yolo/reset_tracker` – resets tracker state.

- **WebSockets**
  - Live Webcam: `/ws/count` when `model` is a YOLO variant understood by `yolo_model_map`.
    - Currently blocked by W‑001/W‑002 (frontend sends `"yolov8"` without variant suffix).
  - External Camera: `/ws/external-camera` with `model` set to YOLO variant.
  - Video Upload: `/ws/video-process` with `model` set to YOLO variant.

### Outputs

- Base prediction:

  - `count` (float/rounded), `inference_time_ms`, `device`.
  - `boxes`: structured bounding boxes + confidence.
  - `average_confidence`, `min_confidence`, `max_confidence` as applicable.

- Visualization:

  - `annotated_image` (REST) or `heatmap` (WebSocket) – both are data URLs of the original frame overlaid with boxes.

- Tracking (when `enable_tracking` and `UnifiedCounter` are active):
  - `tracks`: each containing `id`, `box`, `position`, `state`, `trajectory`, `frames_tracked`, speed.
  - `unique_count`: number of distinct IDs.
  - `speed_stats`: distribution stats for per-frame speeds.
  - `advanced_metrics`: optional density & speed metrics computed via PedPy over trajectories.

### Input modes

- **Upload Image**: detection & visualization via REST.
- **Live Webcam**: intended to provide real-time detection + tracking overlays once W‑001/W‑002 are fixed.
- **External Camera**: actively used through the gated router and/or UnifiedCounter.
- **Video Upload**: core model for frame-by-frame analysis and trajectory visualization.

### Notes

- YOLO is the only model with **full tracking + speed + advanced metrics** integration.
- Most rich visualization stories (bounding boxes, trajectories, speed heatmaps) depend on this stack working end-to-end.

## MCNN (Legacy / Roadmap)

### Role

- Legacy **multi-column CNN** model; intended as an additional density-based baseline.
- Mentioned in configs and UI but not fully wired into all streaming paths.

### Checkpoints & config

- `UnifiedCounter` supports `model_type == 'mcnn'` with default checkpoint:
  - `ml/checkpoints/mcnn.pth` (see `UnifiedCounter.__init__`).
- Top-level config primarily highlights CSRNet and TMTB; MCNN paths are more implicit.

### API surface

- No dedicated **REST** endpoint in `app/api/v1/endpoints` (unlike CSRNet/TMTB/YOLO).
- Some support exists via `UnifiedCounter` for batch/video scenarios.
- **Video UI** exposes `"mcnn"` as a selectable model, but:
  - `/ws/video-process` does not currently implement an MCNN branch (W‑005).

### Outputs

- When used via `UnifiedCounter` (where implemented), MCNN would behave similarly to CSRNet/TMTB:
  - Density maps, counts, and potentially overlays.
  - No special tracking semantics distinct from the YOLO case.

### Input modes

- **Upload Image**: not exposed via a first-class REST endpoint.
- **Live Webcam**: not explicitly wired.
- **External Camera**: not part of the current gated router configuration.
- **Video Upload**: appears in the UI but is unsupported on the backend (W‑005).

### Notes

- MCNN should be treated as **roadmap / experimental** until its endpoints and WebSocket branches are implemented and tested.
- In the near term, it is safer to **hide or disable** MCNN options in UI flows where there is no backend support.
